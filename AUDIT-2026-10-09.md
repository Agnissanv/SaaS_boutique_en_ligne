## 🔴 Priorité haute

### 1. XSS stockée via le JSON-LD de la page boutique
- **Où** : `src/app/(public)/[shopSlug]/page.tsx:191` (aussi `faq/page.tsx:113` et `layout.tsx:229`, ces deux-là sans donnée utilisateur).
- **Problème** : `name` et `description` d'une boutique, saisis par le vendeur, sont injectés dans un `<script type="application/ld+json">` avec `JSON.stringify` seul. Un vendeur qui met `</script><script>…</script>` dans sa description (300 caractères suffisent, aucune sanitisation) exécute du JavaScript chez chaque visiteur de sa boutique. La CSP autorise `'unsafe-inline'`, donc elle ne protège pas.
- **Correctif** : échapper `<` après la sérialisation (`JSON.stringify(x).replace(/</g, "\\u003c")`), dans les 3 endroits. Idéalement une petite fonction partagée.

### 2. Un vendeur peut s'attribuer « Boutique vérifiée » et le meilleur classement
- **Où** : `supabase/migrations/0042_shop_plan_rank_and_verified.sql`, politique `shops_owner_all` (0001).
- **Problème** : la politique `for all` laisse le propriétaire modifier toutes les colonnes de sa boutique. Des triggers protègent `status`, `view_count` et le branding, mais **pas `is_verified` ni `plan_rank`**. Avec sa propre session et l'API REST, un vendeur peut passer `is_verified = true` et `plan_rank` au meilleur rang, sans payer.
- **Correctif** : un trigger `BEFORE UPDATE` sur le modèle de `prevent_view_count_tampering` (0036) qui refuse ces deux colonnes hors admin / hors fonction de synchro des plans.

### 3. Next.js 16.3.5 : 1 vulnérabilité critique et plusieurs hautes
- `npm audit` : Next.js 16.0.0–16.3.7 (RCE dans `next/og`, empoisonnement de cache SSG/ISR, SSRF dans l'optimisation d'images, fuite en mode brouillon…), plus `sharp` et `source-map-js`.
- **Exposition réelle plutôt limitée** : le projet n'utilise ni `ImageResponse`, ni `use cache`, ni le mode brouillon, et il est sur Vercel. Mais l'optimiseur d'images est actif (voir point 14).
- **Correctif** : `npm install next@16.4.0 eslint-config-next@16.4.0`, puis `npm audit fix` pour `sharp` et `source-map-js`. Relancer `npm run build`.

### 4. Données privées des vendeurs lisibles par tout le monde (à confirmer)
- **Où** : `shops_public_read_active` (0001) : lecture publique de la **ligne entière**.
- **Problème** : `notification_email`, `owner_id`, `mobile_money_number` sont des colonnes de `shops`, donc lisibles avec la clé anonyme publique : `GET /rest/v1/shops?select=notification_email,owner_id`. N'importe qui peut collecter les emails des vendeurs (spam, hameçonnage).
- **Test à faire toi-même** (clé anonyme, lecture seule) : ouvrir dans le navigateur ou avec curl `https://<projet>.supabase.co/rest/v1/shops?select=notification_email,owner_id&limit=5` avec l'en-tête `apikey: <ANON_KEY>`.
- **Correctif** : sortir les colonnes privées dans une table `shop_private` (RLS propriétaire uniquement), ou retirer les droits de colonne (`revoke select (…) on shops from anon, authenticated`) et lire ces champs via une fonction `security definer`.

### 5. Commandes anonymes sans aucune limite : vidage du stock et spam
- **Où** : `create_order` (0031), appelable par `anon`, depuis `cart-checkout.tsx:148`.
- **Problème** : pas de limitation de débit (la table `endpoint_rate_limits` n'est utilisée que par la recherche et le formulaire de contact), pas de captcha, aucune borne sur la longueur du nom, de l'adresse ou de l'email, ni sur la quantité hors stock. Chaque commande **décrémente le stock immédiatement** et crée une notification au vendeur. Un script peut vider le stock de n'importe quelle boutique et noyer le vendeur de notifications, y compris les push.
- **Correctif** : passer la création de commande par une Server Action (`checkRateLimit` + captcha Cloudflare Turnstile), ajouter des bornes de longueur dans la fonction, un plafond de quantité et un plafond de commandes en attente par téléphone.

### 6. Le stock n'est jamais remis quand une commande est annulée
- **Où** : `cancel_order` (0030) et l'annulation côté vendeur : aucune ligne ne remet `stock`, ni ne décrémente `promo_codes.used_count`.
- **Problème** : chaque annulation (client ou vendeur) fait perdre définitivement du stock. En combinaison avec le point 5, c'est irréversible sans intervention manuelle.
- **Correctif** : restituer le stock des `order_items` (et les variantes) et le compteur du code promo dans `cancel_order` et dans le passage au statut `cancelled`.

Créer une fonction `get_shops_ratings(ids[])` comme `get_products_ratings` existe déjà, et mettre en cache (`unstable_cache` / ISR) la partie non liée à la localisation.
